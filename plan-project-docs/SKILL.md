# Plan Project Docs

把正式 plan 或项目证据转换为后续开发真正需要的 `docs/planning/`，并在项目状态变化后保持文档一致。规划文档描述稳定的目标、约束和维护契约；不要把过期快照、运行日志或未经验证的计划写成当前事实。

## 工作模式

- **Plan 归档**：保存用户已认可的正式 plan。
- **执行前准备**：执行大型 plan 前先创建或更新项目指导文档。
- **现有项目梳理**：为缺少相关文档的现有项目生成最小文档集合。
- **状态同步与审计**：实现、测试、部署、重命名、范围变化、暂停或取消后，核对并修正文档漂移。已有 `docs/planning/` 时默认进入此模式，不要只在旧文档末尾追加新状态。

如果既没有具体 plan，也不是明确的项目文档生成、同步或审计请求，先要求用户明确目标，不自行扩展范围。

## 核心规则

1. **分开目标与事实**：plan 只能证明目标或决策，不能证明已经实现、验证或部署。
2. **当前状态必须新鲜**：代码、测试、配置、Git 和运行环境可能变化。写“当前”前先在本次任务中验证，并记录验证日期与证据；无法验证时写 `待确认`。
3. **更新不是追加**：新证据推翻旧状态时，替换或重分类旧表述；历史记录移入明确标注的历史章节或独立 dated artifact，不保留互相冲突的“当前状态”。
4. **索引始终同步**：新增、删除、重命名或实质更新任何 planning 文档时，同时更新 `docs/planning/README.md`。
5. **文档选择会变化**：每次同步都重新评估文档集合。项目进入发布、持久化、外部 API 或生产运维阶段后，不能沿用早期“无需该文档”的判断。
6. **最小且不重复**：已有同用途文档时优先链接或更新，不在 `docs/planning/` 再复制一份。

## 工作流

### 1. 确认来源与项目根目录

- 使用对话中用户最新认可的正式 plan；多个版本冲突时使用最新认可版本。
- 从 cwd 或用户路径确认项目根目录。先检查 `git status --short --branch`，保护已有改动。
- 记录本次模式、审计日期、项目根目录，以及是否能访问运行时或部署证据。

### 2. 建立证据与状态清单

- 优先读取 `AGENTS.md`、根 `README*`、已有 `docs/`、包/构建清单、应用入口、路由/API/schema、测试、部署配置和近期相关 Git diff/log。
- 已有 planning 文档时，先列出其中所有当前状态、未完成项、跳过决定、命令和路径，再与项目证据核对。
- 状态同步或包含外部运行状态时，完整读取 `references/state-consistency.md`，按其中的证据优先级、状态标签和一致性清单执行。
- 不用文件名、旧文档、会话记忆或 plan 推断 API、数据库、部署状态、测试结果、时间线或负责人。
- 外部状态无法安全验证时，保留最后一次带日期的事实，并明确它不是当前确认结果。

### 3. 选择最小文档集合

- 完整读取 `references/document-catalog.md`。
- 默认从索引加 1–3 篇核心文档开始；复杂项目或重大变更才增加。
- 先合并后拆分：同一批维护决策优先放在 PRD 或技术设计中。
- 重新检查既有跳过项是否仍成立；范围变化时创建、合并、链接或退役对应文档。
- 小型 bug fix 或窄重构只需要最小 planning note；纯文档修正不自动生成测试或发布文档。

### 4. 创建或同步文档

- 默认只修改目标项目的 `docs/planning/`，除非用户明确包含根 README 或其他文档。
- 保留仍然准确的人工内容；删除、替换或标记已经失效的状态，不用“新增一段最新说明”掩盖旧冲突。
- 每篇文档说明目的、适用范围、证据或 plan 来源、非目标、实现/维护指引、验收方式和待确认项；不适用的空章节可省略。
- 使用明确状态词：`计划中`、`已实现未验证`、`已验证`、`已部署`、`已暂停`、`已取消`、`历史记录`、`待确认`。
- dated 运行记录、burn-in/soak 日志和一次性 deployment 证据默认不作为长期 planning 文档；需要保留时标记为历史，并在索引说明当前状态应从哪里读取。

### 5. 做一致性与可执行性检查

- 对照 `references/state-consistency.md` 检查跨文档状态、旧名称、旧路径、旧命令、日期和跳过项。
- 运行项目最小相关验证，确认写入的命令与测试结果；未运行的检查不得写成通过。
- 如果 skill 目录中的脚本可用，运行：

  ```bash
  python3 <skill-dir>/scripts/audit_planning_docs.py --root <project-root>
  ```

- 脚本只验证 planning 文件是否进入索引及本地 Markdown 链接是否存在；语义状态仍需人工核对。

### 6. 汇报

- 列出生成、更新、合并、退役和有意跳过的文档。
- 对审计请求，按“吻合 / 失配 / 待确认”汇报，并给出每项证据。
- 列出实际运行的检查及结果；区分仓库检查、运行时探针和未验证外部状态。
- 列出需要用户确认的事项，以及为什么不能从当前证据确定。

## Planning 索引要求

`docs/planning/README.md` 是维护索引，不是项目销售页。它必须包含：

- 请求或 plan 标题、工作模式、审计/更新时间和项目根目录；
- 项目是什么，以及当前已验证状态与目标状态的简短区分；
- 本次实际检查的关键证据和验证命令；
- 已生成、已更新、已链接、已退役和已跳过文档；
- 当前待确认项；没有时明确写“无”；
- 历史运行记录的定位，以及获取当前运行状态的权威来源（如适用）。

不要把旧生成时间继续写成“当前状态时间”，也不要把所有历史调试过程塞进索引。

## 根 README 规则

只有用户明确要求，或任务范围明确包含根 README 同步时才修改根 README。此时：

- 开头简洁说明项目是什么、解决什么问题、适合谁；提供证据支持的最短运行方式。
- 截图、Demo、对比、Roadmap、License 和贡献章节均按项目需要选择，不是强制模板；没有信息时不要为了凑章节制造大量 `待确认`。
- 不写与后文冲突的营销短句；例如 ES Modules 需要本地服务器时，不得同时声称可双击运行。
- 部署地址、自动部署、版本号和测试通过数属于易漂移事实，必须附验证日期和证据，或改写成稳定的操作说明。

## 文件与安全边界

- 不修改产品代码、测试、配置、依赖、部署文件、secrets 或 `.env`。
- 不写入 secret、token、私钥、Cookie 或环境变量值。
- 用户使用中文时默认写中文；技术名、路径、API 和命令保持原样。
- 缺少证据时写具体的 `待确认` 问题，不编造功能、schema、路由、凭据、竞品、时间线或负责人。

## 资源

- `references/document-catalog.md`：文档选择、合并、链接与跳过规则；每次使用都完整读取。
- `references/state-consistency.md`：状态同步、证据优先级、历史隔离和跨文档审计；更新或审计已有文档时完整读取。
- `scripts/audit_planning_docs.py`：确定性检查索引覆盖和本地 Markdown 链接。
