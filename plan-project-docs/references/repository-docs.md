# 仓库级配套文档

仅当任务范围明确包含根 README 或开发者指南的创建/同步时读取。

本文沿用以 skill 目录为起点的 `references/` 路径。

## 根 README 规则

只有用户明确要求，或任务范围明确包含根 README 同步时才修改根 README。此时：

- **先定读者再动笔**：根 README 默认面向第一次打开仓库的人（可能是使用者、合作方或公众），不是维护者。开头简洁说明项目是什么、解决什么问题、适合谁；涉及信任的开诚布公（隐私、数据边界等按项目实际写，不营销化）。
- **技术内容只保留最短运行方式**：前置条件 + 启动/构建命令（须有证据支持）。只有当现有开发者指南已经覆盖对应内容，或任务范围明确包含创建/同步开发者指南时，才从 README 移除架构、目录结构、CI、开发约定、部署细节等维护者向内容并改为链接（见下节）。否则保留仍有用的技术内容，压缩成不干扰首次访问者的技术章节，并把拆分建议列为待确认，不自行扩大范围。
- **尊重现有 README 的定位与人工内容**：如果已有内容面向公众且写得清楚，保持公众可读，不混入只有维护者关心的术语、内部命令与约定；任务范围允许做"公众部分 + 技术部分"拆分时，公众部分原样保留，由开发者指南承载技术部分，不借拆分之名重写公众文案。
- 截图、Demo、对比、Roadmap、License 和贡献章节均按项目需要选择，不是强制模板；没有信息时不要为了凑章节制造大量 `待确认`。
- 不写与后文冲突的营销短句；例如 ES Modules 需要本地服务器时，不得同时声称可双击运行。
- 部署地址、自动部署、版本号和测试通过数属于易漂移事实，必须附验证日期和证据，或改写成稳定的操作说明。

## 开发者指南规则

开发者指南（通常 `docs/developer-guide.md`）是**代码现状文档**：写给完全不了解项目的技术开发者，目标是读完能理解系统的实际实现逻辑，并能独立完成常见修改。它与 planning 文档定位不同——planning 描述设计意图与需求基线，指南描述代码现在如何实现。关于当前实现的表述不一致时以本次代码证据为准；未实现的目标需求继续保留在 planning 中，并明确标记实现差距。

- 是否需要生成、应包含什么，按 `references/document-catalog.md` 的「仓库级配套文档」一节判断；小项目 README 已足够时不要制造。
- 创建时在文首声明与 `docs/planning/` 的分工，并在 planning 索引中反向链接、说明冲突优先级。
- 内容以本次核实的代码证据为准：结构性数字（集合数、端点数、路由清单、端口约定等）必须用命令输出验证，不从旧文档或记忆推断。
- 文末写入维护契约：改了它描述的机制，须同 PR 更新本文。
- 不要把它写成第二份设计文档：不写需求背景论证、不写被否决的备选方案（那些属于 planning），只写"现在是什么、在哪改、怎么改"。
