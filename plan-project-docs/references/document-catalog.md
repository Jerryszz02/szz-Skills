# 文档目录

使用本目录决定要在 `docs/planning/` 下生成哪些文件。只生成对后续实现或维护有实际帮助的最小文档集合。文末「仓库级配套文档」一节覆盖不属于 planning 的配套文档（开发者指南）。

## 选择规则

- 每次都生成或更新 `README.md` 作为 planning 索引。
- 优先生成少量具体文档，而不是完整模板套件；默认从 `README.md` 加 1-3 篇核心文档开始判断。
- 先合并后拆分：只有当某类信息有独立维护者、独立验收方式、独立风险，或篇幅会明显干扰核心文档时，才单独成篇。
- 如果某个文档只会重复另一个 planning 文档、plan、`SKILL.md`、README 或代码中已经清楚表达的内容，就不要生成；把必要摘要合并进更核心的文档。
- 常见合并方向：项目背景和目标优先并入 `prd.md`；用户流程和失败状态优先并入 `prd.md`；架构边界、实现契约和关键决策优先并入 `technical-design.md`；安全边界足够重要时保留 `security-privacy.md`；验证方式足够独立时保留 `test-plan.md`。
- Plan 归档模式下，当 plan 改变产品行为、架构、数据、API、用户流程、安全边界、发布流程或运维方式时，对应文档才需要生成。
- 现有项目梳理模式下，当仓库证据足以说明产品行为、架构、数据、API、用户流程、安全边界、发布流程或运维方式时，对应文档才需要生成。
- 状态同步模式下，既有文档选择不是永久决定。实现、测试、发布、运维或产品范围变化后，必须重新评估已生成与已跳过项；必要时创建、合并、链接或退役文档。
- 仓库已有同用途的 `docs/architecture.md`、`docs/runbook.md`、`docs/app-store/`、API schema 或发布清单时，优先从 planning 索引链接并说明权威边界，不重复维护全文。
- dated 验收日志、deployment 记录和逐次运行证据不是默认 planning 文档；长期策略写入 test/release/runbook，历史证据放入明确标注的 dated artifact。
- 如果某个文档只会填充占位内容，或描述 plan 或仓库证据没有触及的子系统，就不需要生成。
- 如果证据不完整但文档仍然必要，对未知项写 `待确认`，并说明它依赖什么信息。

## 文档清单

### `project-brief.md`

目的：说明项目为什么存在，以及这份 plan 或当前项目文档生成请求试图达成什么结果。

需要生成：
- 启动新项目；
- 开始主要功能或产品方向；
- 现有项目缺少 brief，且仓库证据足以说明项目目的、受众、范围或约束；
- 成功标准、受众、范围或约束需要在后续工作中持续可见。

不需要生成：
- 任务只是窄范围 bug fix、清理或小实现细节；
- 背景、目标、受众、非目标和成功标准可以简洁放进 `prd.md`；
- 项目很小，单独 brief 只会重复 README、plan 或 PRD；
- 仓库里已有覆盖同一 plan 或当前项目状态的最新 brief。

应包含：
- 背景和问题定义；
- 目标用户或操作人员；
- 目标和非目标；
- 成功指标或验收结果；
- 范围边界；
- 约束、假设和依赖。

### `prd.md`

目的：定义实现完成后必须存在的产品行为。

需要生成：
- plan 新增或改变用户可见行为，或仓库证据足以说明已有用户可见行为；
- 工作流、权限、内容、UX 状态或业务规则需要落地；
- 验收依赖产品需求，而不只是代码结构。

不需要生成：
- 改动完全是内部实现，没有产品行为变化；
- plan 或项目证据纯粹是基础设施或开发者工具。

应包含：
- 用户和使用场景；
- 功能需求；
- 非功能需求；
- 状态、权限和边界情况；
- 验收标准；
- 明确的非目标。

### `architecture.md`

目的：解释实现必须遵守的系统形态和边界。

需要生成：
- plan 触及多个模块、服务、包或应用，或仓库证据显示项目已有多个模块、服务、包或应用；
- 存在重要依赖、数据流、部署边界或所有权边界；
- 长期可维护性或可扩展性是核心问题。

不需要生成：
- 改动只局限在一个组件内，且本地行为明显；
- 项目只是单个 package、单个 skill、单个脚本或少量文件，模块职责可放进 `technical-design.md`；
- 架构内容主要是在列文件职责、数据流或外部依赖，且不会形成独立设计约束；
- 已有架构文档已经覆盖同一设计，只需要从索引指向它。

应包含：
- 模块或服务职责；
- 数据流或控制流；
- 外部依赖；
- 相关部署或运行时形态；
- 安全和信任边界；
- 被否决的重要备选方案。

### `technical-design.md`

目的：把 plan 或项目证据转换为具体实现与维护指引。

需要生成：
- 实现包含非平凡逻辑、顺序、状态处理、兼容性问题或集成细节；
- 另一个工程师需要不用重新决策就能实现。

不需要生成：
- 改动是单文件机械编辑或明显 bug fix；
- plan 本身或已有项目文档已经足够作为详细实现规格。

应包含：
- 选定方案；
- 受影响子系统；
- 数据或状态流；
- 错误处理和 fallback 行为；
- 兼容性约束；
- 任务拆分；
- 验收指引。

### `user-flow.md`

目的：描述用户或操作人员如何完成体验流程。

需要生成：
- plan 新增或改变 UI、CLI、onboarding、权限或操作流程，或仓库证据足以说明已有操作流程；
- 错误、空状态、加载、取消或重试状态很重要。

不需要生成：
- 没有用户或操作人员交互变化；
- 行为完全是后端或内部实现。
- 主流程、失败流和验收场景可以自然放进 `prd.md`，单独成篇只会重复产品需求。

应包含：
- 入口和出口；
- 主流程；
- 备用流程和失败流程；
- 权限或角色差异；
- UI/CLI 状态和文案敏感决策；
- 验收场景。

### `api-design.md`

目的：定义服务边界和请求/响应契约。

需要生成：
- plan 新增、删除或改变 HTTP/RPC/GraphQL/WebSocket/CLI/plugin API，或仓库证据足以说明已有 API 契约；
- 客户端和服务端需要稳定契约；
- 错误处理、鉴权、分页、幂等或版本策略很重要。

不需要生成：
- 没有 API 契约变化；
- API 行为已经在现有契约文件中完整定义，只需要索引指向它。

应包含：
- endpoint 或 operation；
- 请求和响应结构；
- 认证和授权；
- 校验规则；
- 错误和状态码；
- 相关分页、幂等和版本策略；
- 兼容性说明。

### `database-design.md`

目的：定义持久化数据改动。

需要生成：
- plan 新增、删除或改变表、文档、集合、索引、迁移或持久化语义，或仓库证据足以说明已有持久化语义；
- 数据保留、回填、一致性或回滚很重要。

不需要生成：
- 没有持久化变化；
- 数据变化只涉及内存状态或本地缓存，没有持久化 schema 影响。

应包含：
- 实体和关系；
- 字段及含义；
- 索引和约束；
- 迁移和回滚计划；
- 数据生命周期和保留策略；
- 回填或兼容性说明。

### `security-privacy.md`

目的：记录安全、隐私和信任边界决策。

需要生成：
- plan 处理用户数据、凭据、权限、外部服务、文件访问、网络调用、浏览器自动化、支付或敏感操作，或仓库证据显示项目已有这些边界；
- 访问控制、审计、数据最小化或滥用防护很重要。

不需要生成：
- 改动没有有意义的安全或隐私影响；
- 相关控制没有变化，并且已经在其他地方记录。

应包含：
- 敏感数据和数据分级；
- 认证和授权；
- secrets 处理；
- 信任边界；
- 审计和日志预期；
- 隐私约束；
- 威胁、缓解措施和剩余风险。

### `test-plan.md`

目的：定义如何验证实现。

需要生成：
- plan 改变行为、架构、数据、API 或用户流程，或仓库证据足以说明已有行为、架构、数据、API 或用户流程；
- 验收标准需要可执行或人工验证。

不需要生成：
- 改动仅为文档，索引已经记录 review 检查；
- plan 是没有行为影响的简单文字编辑。

应包含：
- 适用的单元、集成、E2E、人工、性能和安全检查；
- fixture 或测试数据；
- 回归场景；
- 验收标准；
- 已知可运行命令；
- 测试未覆盖的风险。

更新要求：实际执行测试、测试数量变化或新增验证工具后，必须同步旧的“未执行/非目标”状态；不能只在另一篇 README 中记录通过结果。

### `release-plan.md`

目的：定义改动如何安全到达用户。

需要生成：
- 部署、迁移、feature flag、分阶段发布、数据回填或回滚策略很重要；
- 项目有生产用户或运维风险。
- 项目从本地开发进入 TestFlight、App Store、公开托管或其他正式发布准备，且现有发布资料需要统一入口。

不需要生成：
- 改动只在本地、仅为文档，或不通过部署路径发布；
- 发布机制没有变化且非常简单。

应包含：
- 发布顺序；
- feature flag 或分阶段曝光；
- 迁移和回填顺序；
- 回滚步骤；
- 监控和告警；
- 发布 checklist。

### `operations-runbook.md`

目的：帮助操作人员运行和排查最终系统。

需要生成：
- plan 新增或改变服务、定时任务、长期运行进程、队列、外部集成或生产运维行为，或仓库证据显示项目已有这些运行时形态；
- 未来事故处理需要具体命令或日志位置。

不需要生成：
- 没有运行时或运维行为变化；
- 现有 runbook 仍然准确，只需要索引指向它。

应包含：
- 启动、停止、重启步骤；
- 不含 secret 值的配置位置；
- 日志和健康检查；
- 常见失败模式；
- 排查步骤；
- 相关备份、恢复和灾难恢复说明。

### `decision-log.md`

目的：保留重要决策和取舍。

需要生成：
- plan 在产品、架构、供应商、模型、数据或发布方案之间做了重要选择，或仓库证据显示项目已有需要记录的关键取舍；
- 未来维护者否则会重新打开同一个决策。

不需要生成：
- 没有有意义的备选方案或取舍；
- 决策只是小实现细节；
- 决策数量少，且可以作为 `prd.md` 或 `technical-design.md` 的“关键决策”章节维护。

应包含：
- 决策日期；
- 决策结论；
- 背景；
- 考虑过的选项；
- 理由；
- 后果和需要重新评估的触发条件。

## 仓库级配套文档（不在 `docs/planning/` 下）

以下文档属于仓库级文档，不进入 planning 索引的"已生成文档"表；存在时在索引中单列说明权威边界并互链。

### `docs/developer-guide.md`（开发者指南 / 代码现状文档）

目的：让完全不了解项目的技术开发者读完后能理解系统的实际实现逻辑，并能独立完成常见修改（加字段、加接口、加页面、改规则）。描述**代码现状**，不描述设计意图——设计意图与需求基线属于 planning 文档。关于当前实现的表述不一致时以本次代码证据为准；未实现的目标需求继续保留在 planning 中，并明确标记实现差距。

以下条件只用于判断开发者指南是否有维护价值，不自动扩大任务范围；仅在用户明确要求，或任务范围明确包含创建/同步开发者指南时修改该文件。

需要生成：

- 项目有非平凡的服务端业务规则、权限模型、状态机或多层数据流，新维护者仅读代码的上手成本明显高于维护一份指南的成本；
- 技术栈或框架存在需要口耳相传的坑（非常规约束、隐式约定、必须同步修改的多处副本、版本锁定点）；
- 项目预期有其他开发者或 agent 长期参与维护、接手或交接；
- 根 README 的技术部分已膨胀到干扰公众读者，且任务范围允许把技术内容拆到开发者指南。

不需要生成：

- 项目很小：单脚本、单 package、少量文件，README 的最短运行方式加代码注释已足够；
- 内容只会复述 README、planning 文档或代码注释，没有增量信息；
- 一次性项目，不预期第二个人阅读或维护。

应包含：

- 文首定位声明：这是代码现状文档，写明与 `docs/planning/` 设计文档的分工；代码只对当前实现事实具有优先级，planning 继续保留已认可的目标需求；
- 项目一页纸：是什么、核心角色/业务闭环、技术形态；
- 仓库地图（含哪些目录不入库）与本地开发环境（含实测踩坑）；
- 架构心智模型：少量关键原则（如写入收口位置、权限在哪层强制、删除语义约定），不展开设计论证；
- 后端/前端/数据模型的现状详解；结构性数字（集合数、端点数、路由清单、端口约定）必须本次用命令输出核实；
- 端到端业务流程：把各层串起来，说明一条数据从哪里进哪里出；
- 常见修改食谱：加字段/加接口/加页面/改规则分别动哪些文件、补哪些测试；
- 测试、CI、部署速览与红线速查（改代码前必读的硬约定）；
- 文末维护契约：改了本文描述的机制，须同 PR 更新本文。

不应包含：

- 需求背景论证、被否决的备选方案、未来规划（属于 planning 文档）；
- 逐行文件清单式的内容复制（读者会自己读代码，指南负责指路而非替代阅读）；
- 易漂移且无法稳定验证的运行时状态（按 state-consistency.md 的历史隔离规则处理）。

维护要求：

- 随代码同 PR 更新；状态同步或审计已有文档时，把它列入漂移检查对象（见 state-consistency.md）。
- 与 planning 索引互链，各自声明分工；索引中说明"当前实现以代码及开发者指南为准，本目录保留设计与需求基线"。
