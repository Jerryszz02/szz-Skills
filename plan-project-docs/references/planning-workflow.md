# Planning 文档工作流与索引

创建、更新或审计 `docs/planning/` 时，按下列步骤处理。本文的 `references/` 和 `scripts/` 路径以 skill 目录为起点。

## 工作流

### 1. 确认来源与项目根目录

- 使用对话中用户最新认可的正式 plan；多个版本冲突时使用最新认可版本。
- 从 cwd 或用户路径确认项目根目录。先检查 `git status --short --branch`，保护已有改动。
- 记录本次模式、审计日期、项目根目录，以及是否能访问运行时或部署证据。

### 2. 建立证据与状态清单

- 优先读取 `AGENTS.md`、根 `README*`、已有 `docs/`、包/构建清单、应用入口、路由/API/schema、测试、部署配置和近期相关 Git diff/log。
- 已有 planning 文档时，先列出其中所有当前状态、未完成项、跳过决定、命令和路径，再与项目证据核对。
- 状态同步或包含外部运行状态时，完整读取 `references/state-consistency.md`，按其中的证据优先级、状态标签和一致性清单执行。
- 不用文件名、旧文档、会话记忆或 plan 推断 API、数据库、部署状态、测试结果、时间线或负责人。
- 外部状态无法安全验证时，保留最后一次带日期的事实，并明确它不是当前确认结果。

### 3. 选择最小文档集合

- 需要选择或重新评估文档集合时，完整读取 `references/document-catalog.md`。
- 默认从索引加 1–3 篇核心文档开始；复杂项目或重大变更才增加。
- 先合并后拆分：同一批维护决策优先放在 PRD 或技术设计中。
- 重新检查既有跳过项是否仍成立；范围变化时创建、合并、链接或退役对应文档。
- 小型 bug fix 或窄重构只需要最小 planning note；纯文档修正不自动生成测试或发布文档。
- 评估是否需要仓库级配套文档（根 README 之外的开发者指南）：按 `references/document-catalog.md` 的「仓库级配套文档」一节判断，不适用时不强行创建。

### 4. 创建或同步文档

- 默认只修改目标项目的 `docs/planning/`；根 README 和 `docs/` 下开发者指南同理，只在用户明确要求或任务范围明确包含时修改。
- 保留仍然准确的人工内容；删除、替换或标记已经失效的状态，不用“新增一段最新说明”掩盖旧冲突。
- 每篇文档说明目的、适用范围、证据或 plan 来源、非目标、实现/维护指引、验收方式和待确认项；不适用的空章节可省略。
- 使用明确状态词：`计划中`、`已实现未验证`、`已验证`、`已部署`、`已暂停`、`已取消`、`历史记录`、`待确认`。
- dated 运行记录、burn-in/soak 日志和一次性 deployment 证据默认不作为长期 planning 文档；需要保留时标记为历史，并在索引说明当前状态应从哪里读取。

### 5. 做一致性与可执行性检查

- 更新或审计已有文档、涉及外部运行状态时，对照 `references/state-consistency.md` 检查跨文档状态、旧名称、旧路径、旧命令、日期和跳过项。
- 运行项目最小相关验证，确认写入的命令与测试结果；未运行的检查不得写成通过。
- 如果 skill 目录中的脚本可用，运行：

  ```bash
  python3 <skill-dir>/scripts/audit_planning_docs.py --root <project-root>
  ```

- 脚本只验证 planning 文件是否进入索引及本地 Markdown 链接是否存在；语义状态仍需人工核对。

### 6. 汇报

- 列出生成、更新、合并、退役和有意跳过的文档。
- 对审计请求，按“吻合 / 失配 / 待确认”汇报，并给出每项证据。
- 列出实际运行的检查及结果；区分仓库检查、运行时探针和未验证外部状态。
- 列出需要用户确认的事项，以及为什么不能从当前证据确定。

## Planning 索引要求

`docs/planning/README.md` 是维护索引，不是项目销售页。它必须包含：

- 请求或 plan 标题、工作模式、审计/更新时间和项目根目录；
- 项目是什么，以及当前已验证状态与目标状态的简短区分；
- 本次实际检查的关键证据和验证命令；
- 已生成、已更新、已链接、已退役和已跳过文档；
- 当前待确认项；没有时明确写“无”；
- 历史运行记录的定位，以及获取当前运行状态的权威来源（如适用）。

不要把旧生成时间继续写成“当前状态时间”，也不要把所有历史调试过程塞进索引。
